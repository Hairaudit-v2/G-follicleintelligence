# FI-TEAM-COHESION-B1.2 — Access Identity Proof

**Status:** GREEN (2026-08-05)  
**Predecessor:** [b1.1-directory-identity-proof.md](./b1.1-directory-identity-proof.md)

## What landed

Canonical Staff Access Centre loader (`src/lib/workforce/staffAccessCentre.server.ts`) now consumes:

```ts
resolveStaffIdentities({ tenantId, by: "staffMemberId", staffMemberIds })
```

and projects via `@/src/lib/team/access`:

- `StaffAccessEntry` (presentation DTO — not the full `StaffIdentity`)
- `attentionReasons` for incomplete / ambiguous / invalid links and terminated-with-active-access
- Action flags bridged onto legacy `StaffAccessCentreRow` for the existing UI

Access continues to own login-invite status, PIN labels, auth enrichment, and mutation eligibility. Identity integrity warnings are surfaced without inventing invite / suspend / revoke decisions.

Dual-table writes required by invite provisioning and access suspend remain in `staffTenantLinkRepair.server.ts` (already allowlisted).

## Behavioural rule

Partial / invalid identities are **not** hidden. Lifecycle staff without a scheduling projection remain visible with:

- `scheduling_record_missing`
- `identity_link_incomplete`
- and/or `missing_auth_identity` when linked but no auth user yet

Ambiguous / cross-tenant / invalid targets:

- show `identity_requires_reconciliation` (or mismatch/invalid attention)
- suppress invite / destructive UI flags
- server mutations reject with a reconciliation error before touching access state

Scheduling-only staff are **not** invented as access rows (access workflow remains lifecycle-sourced). Lifecycle-only staff stay included where the access centre already listed them.

**B1.1.1** (lifecycle-only directory visibility) remains deferred — access proof may inform where those records belong later.

## Safety preserved

| Concern | Disposition |
|---------|-------------|
| Onboarding invite vs login invite | Untouched — login invites only (`fi_staff_login_invitations`) |
| No auth user yet | Visible; invite eligibility from existing access rules |
| Accepted login invite | `resolveInviteStatus` / `canReceiveLoginInvite` unchanged |
| PIN setup | Still `loadStaffPinMetadataForStaff` + pin layer mutations |
| Suspended vs terminated employment | Distinct auth login statuses + terminated-with-active-access attention |
| Revoked without deleting history | Revoke still retains member row; invitations marked revoked |
| Token routes | Accept / PIN token modules not rewritten |
| `canManage` / entitlement | Actions still gated by `assertWorkforceHrManageAllowed` |
| Audit events | Existing `insertStaffAccessAuditEvent` paths retained |
| Tenant isolation | Batch resolve scoped by tenant; cross-tenant integrity hard-fails / blocks |

## Performance

Identity resolution for the access list uses a **fixed** data-access budget inside `resolveStaffIdentities` (bounded `.in(...)` loads), not one dual-table join per member. Auth snapshots, invites, and PIN metadata remain access-domain loads.
