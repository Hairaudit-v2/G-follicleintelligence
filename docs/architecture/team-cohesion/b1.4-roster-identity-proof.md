# FI-TEAM-COHESION-B1.4 — Roster Identity Proof

**Status:** GREEN (2026-08-05)  
**Predecessor:** [b1.3-onboarding-identity-proof.md](./b1.3-onboarding-identity-proof.md)

## What landed

Canonical roster eligibility aggregation (`src/lib/workforce-os/rosterEligibleStaff.server.ts`) now consumes:

```ts
resolveStaffIdentities({ tenantId, by: "staffId", staffIds })
```

and projects via `@/src/lib/team/roster`:

- `RosterStaffEntry` (presentation DTO — not the full `StaffIdentity`)
- Scheduling remains the primary roster entity (`staffId` required)
- `attentionReasons` for incomplete / ambiguous / invalid links
- Action flags (`canBeRostered` / `canEditAssignment` / `requiresReconciliation`)
- Member-context bridge into existing `buildRosterStaffEligibilityContext` so eligibility policy is unchanged

Dual-table lifecycle loading via `loadAllTenantStaffMembers` was removed from this path. Lifecycle fields for eligibility come from the identity batch.

New roster mutations (`createStaffShift`, `createAvailabilityBlock`, `assignStaffToClinicalEventAction`) call `assertEligibleRosterIdentityTarget` before writes. Manual adjustment validation surfaces reconciliation as a blocking warning when `allowOverride` is false.

## Behavioural rule — visible vs eligible

| Identity condition | Historical / scheduling presence | New assignment |
|--------------------|----------------------------------|----------------|
| Linked and active | Visible | Domain eligibility unchanged |
| Scheduling-only | Visible + warning | Domain eligibility unchanged (missing lifecycle does **not** auto-exclude) |
| Lifecycle-only | Not a roster row (`projectRosterStaffEntry` returns null) | Not eligible |
| Ambiguous / invalid / cross-tenant | Visible when scheduling row exists | Mutation + action flags blocked |
| Terminated employment | Visible historically | Domain ineligible as today |

## Query budget

Documented and implemented in `loadRosterStaffEligibilityContext`:

1. **One** scheduling load (`loadAllStaffForTenant` or injected `staffRows`)
2. **One** `resolveStaffIdentities({ by: "staffId" })` batch sequence
3. In-memory eligibility evaluation

No per-staff identity query loop.
