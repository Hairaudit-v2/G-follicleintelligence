**Status:** GREEN (2026-08-05)  
**Predecessor:** [b1.8a-payroll-identity-proof.md](./b1.8a-payroll-identity-proof.md)

## What landed

Planning staff subjects resolve through `src/lib/team/planning/`:

```
Schedulable staff population (staffId)
        ↓
One resolveStaffIdentities({ by: "staffId" }) batch
        ↓
projectPlanningStaffEntry (reuses roster/clinical readiness facts)
        ↓
Recruitment candidates → PlanningRecruitmentCandidateRef (non-staff)
Vacancies → PlanningVacancyRef (non-person demand)
        ↓
Procedure optimizer gates candidates via gateProcedureStaffingCandidates
```

**Canonical entity rule:** a recruitment candidate is not a `StaffIdentity`. Vacancies are demand, not people.

## Partial identity behaviour

| State | Behaviour |
|-------|-----------|
| Linked, clinically ready | Normal planning eligibility |
| Scheduling-only | Existing fallback preserved with lifecycle warning |
| Lifecycle-only | `future_capacity_only` — never schedulable |
| Ambiguous / cross-tenant / invalid | No procedure assignment |
| Clinical not ready | Existing readiness blocks assignment |
| Terminated / archived | Excluded from schedulable capacity |
| Candidate / vacancy | Separate types — never forced into StaffIdentity |

## Preserve contracts

Procedure staffing minimums, role/competency requirements, clinic allocation, leave/availability precedence, credential blocks, capacity calculations, recruitment pipeline state, candidate-vs-employee distinction, tenant isolation, and no silent staff creation from candidates remain owned by existing engines. Planning composes signals; it does not rewrite them.
